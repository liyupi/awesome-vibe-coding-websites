# Virtual Pet Companion

Build this website exactly as described below. Replace the [VARIABLES] with your own values; keep everything else.

## Brief
Build [BRAND], an original virtual pet web toy starring [PET_NAME], a [PET_KIND] who lives in [HABITAT]. The first screen is a playable pixel-art habitat, not a promotional hero. Feed, play, clean, and rest actions change four real-time care meters and trigger original sprite reactions. Include two fully playable mini-games that award [COIN_NAME], six wearable outfit items to unlock and equip, local high scores, and versioned localStorage persistence. Use hash views for the pet home, arcade, and wardrobe while keeping one shared live pet state.

- Audience: Developers, creators, students, and designers building a cozy browser game, an interactive portfolio piece, or a small virtual companion for casual play on desktop and mobile.
- Goal: Let a visitor understand the pet's condition at a glance, perform a satisfying care action within five seconds, earn currency through real skill-based play, spend it on visible accessories, and return later to a consistent locally saved companion. Every visible control must perform its described function.
- Tone: Warm, playful, concise, and gently funny without baby talk, guilt, urgency, or punitive mechanics. Use clear US English labels and specific variable-aware messages. The pet can be sleepy or messy but never dies, gets ill, or shames the visitor.

- [COIN_NAME] — Currency name (default: "acorns"). A lowercase plural noun used for balances, rewards, prices, and insufficient-funds messages.

### Layout & motion
- Spacing: Use a 4px base grid and an 8px dominant rhythm. The app maximum width is 1280px with 24px desktop gutters and 12px mobile gutters. Header height is 64px desktop and 56px mobile. Main desktop top padding is 24px; the home grid columns have a 20px gap. Scene and console padding is 16px or 20px. Keep pointer targets at least 48×48px with at least 8px separation. On mobile use 12px panel padding and avoid squeezing four action buttons into one narrow row.
- Radius: Use a crisp pixel silhouette: 12px outer app panels, 8px scene and canvas frames, 4px buttons and meter cards, and 3px Midnight Plum borders. Primary buttons have a hard 4px 4px 0 Midnight Plum shadow that compresses to 1px 1px on press. Avoid glass, soft drop shadows, pill overload, and generic rounded bento cards.
- Motion: The pet idles on a two-frame steps(1,end) loop with one logical pixel of vertical movement every 760ms, a blink every 4.2 seconds, and occasional habitat prop movement. Keep the face and equipped accessory aligned in every frame.
- Motion: Feed, Play, Clean, and Rest select dedicated sprite states for 900ms. Feed drops two snack pixels toward the bowl, Play bounces a small ball once, Clean raises six square bubbles, and Rest dims the habitat by 18 percent and shows two small Z glyphs. Action feedback never blocks the next view navigation.
- Motion: Meter fills update over 180ms with steps(6,end), while numeric values update immediately. Buttons depress with the hard-shadow compression described above. Toasts remain for 2.4 seconds and never cover the pet or primary controls.
- Motion: Hash-view content crossfades for 140ms without route-based scroll-jacking. Wardrobe equips crossfade only the accessory layer for 120ms. Unlocking emits eight tiny square sparkles for 500ms, never full-screen confetti.
- Motion: Mini-games use continuous motion only after explicit Start. Reduced-motion mode removes decorative particles, easing, screen shake, and idle bobbing; game objects move in readable 10fps discrete steps and all results remain legible.
- Motion: Under prefers-reduced-motion outside active games, use static sprite poses, instant meter and accessory changes, no floating hearts or sparkles, and no automatic scene animation. Never flash more than three times per second.
- Imagery: Draw every visual asset in code as original pixel art. Build the habitat as inline SVG on a 160×90 logical grid with shape-rendering='crispEdges', integer coordinates, hard-edged rects and polygons, and no raster texture. Build the pet on a separate 32×32 grid rendered at least 192×192px on desktop. Default [PET_NAME] is a moss bunny with an original square body, two uneven leaf ears, a cream muzzle, coral cheek pixels, and a tiny square tail; do not derive its silhouette from an existing character. Create idle, blink, happy, eating, playing, washing, resting, and needy poses plus independent 32×32 accessory overlays. The default habitat includes a large window, leafy arch, food bowl, toy ball, washing nook, shelf, rug, and small plants. Rewrite and redraw species-specific features, habitat motifs, and falling snacks when PET_KIND or HABITAT changes. Use the same original pet and equipped overlay in home, arcade, and wardrobe. No people, real likenesses, stock images, downloaded sprite sheets, logos, branded props, or text baked into artwork.

## Don'ts
- Do not copy or adapt any existing virtual-pet brand, character species design, mascot, silhouette, signature animation, sprite sheet, screen layout, meter design, icons, sounds, code, prompt, slogans, or exact copy. Implement the specified original pet and interface from scratch.
- Do not use real people's likenesses, anime, game or film characters, celebrity-inspired pets, branded accessories, recognizable product designs, logos, or existing game typography. The default and alternate pets must both be original generic creations.
- Do not use stock photos, downloaded sprite packs, placeholder-image services, external image URLs, Unsplash, Pexels, Pixabay, or generated raster assets. All visual game and habitat art is local SVG, CSS, or Canvas code.
- Do not use a backend, server code, API routes, accounts, authentication, databases, external APIs, analytics, ads, notifications, cloud sync, online leaderboards, or forms that submit anywhere. All simulation and persistence stay in the browser with localStorage.
- Do not fake the simulation. Meters must derive from elapsed real time, all four care actions must apply the exact effects, both mini-games must be playable with working timing and rewards, purchases must debit the exact balance, equipped accessories must render on the pet, and all specified state must survive reload.
- Do not use interval counts as a substitute for timestamps, apply offline decay twice, award currency for idling or repeated early exits, bank a round twice, allow negative currency, or allow invalid saved JSON to crash the app. Clamp values and handle storage failures visibly but nondestructively.
