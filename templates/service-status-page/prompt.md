# Service Status Page

Build this website exactly as described below. Replace the [VARIABLES] with your own values; keep everything else.

## Brief
Build an original single-page service status website for [BRAND], an invented [SERVICE] for [AUDIENCE]. Present a coherent set of fictional operational data: an overall healthy state, six components with fixed 90-day uptime histories, four resolved or completed incident entries with timestamped updates, and a subscription form with an honest static-demo confirmation. Keep all variable-driven copy, component records, daily status values, and incident narratives in src/content.ts; rewrite the service-specific details when the variables change while preserving the layout, record counts, and interaction model.

- Audience: The primary readers are [AUDIENCE] checking whether [BRAND] is available, plus support and operations teams who need a concise public incident record.
- Goal: Let a visitor understand overall health within five seconds, compare component reliability over 90 days, inspect exactly how past incidents progressed, and choose local demo notification preferences without implying that a real subscription occurred.
- Tone: Calm, precise, accountable, and quietly confident. Use plain operational language, useful timestamps, and direct explanations; never turn the page into a sales pitch or manufacture urgency.

## Stack
- Framework: Vite 6 + React 19 + TypeScript
- Styling: Tailwind CSS 4
- Libraries: lucide-react (ISC), @tailwindcss/vite (MIT), @fontsource-variable/manrope (OFL), @fontsource-variable/inter (OFL), @fontsource/ibm-plex-mono (OFL)
- Build: `npm run build` → static files in `dist/`. No backend, no server code, no external APIs.
- Setup:
  - Set the npm build script to tsc -b && vite build; configure Vite with base: './', build.sourcemap: false, and an empty outDir named dist.
  - Use @tailwindcss/vite and @import "tailwindcss" in src/index.css; define the listed colors, fonts, spacing, shadows, and keyframes as CSS custom properties and Tailwind theme tokens.
  - Import Manrope Variable, Inter Variable, and IBM Plex Mono weights 400 and 500 from their Fontsource packages in src/main.tsx so every font file is bundled locally.
  - Keep all default and variable-derived copy, the fixed October sample reference date, six component records, four incident records, and every 90-day status series in src/content.ts; never scatter brand-specific copy through components.
  - Use small React components for the header, aggregate health chart, component row, incident accordion, and subscribe form. Use React state only for chart inspection, incident expansion, and form validation or confirmation; do not add a router or global state library.
  - Represent the 90 daily values as typed arrays committed in src/content.ts, ordered oldest to newest and ending on the fixed sample date October 25. Do not use random values, current-time requests, or remote data.

## Don'ts
- Do not add a backend, serverless function, API route, database, authentication, analytics, third-party status feed, external API request, or form submission to any service; all operational data is fixed local sample data and the subscribe interaction is session-local only.
- Do not claim that emails, alerts, monitoring, uptime checks, or incident updates are actually running. Never display a fake network spinner, randomly refresh health data, or persist email addresses.
- Do not use real status-provider or technology-company names, logos, slogans, product copy, actual incidents, domains, or real uptime figures presented as fact; every brand, metric, and incident must remain explicitly fictional sample content.
- Do not copy an existing status page's exact palette, layout, copy, illustrations, icons, or composition, and do not use brand-specific mascots, custom fonts, or logo sets.
- Do not use photographs, AI-generated bitmaps, stock illustrations, remote images, placeholder-image services, recognizable people, or recognizable brand assets; the polished code-built health panel is the visual anchor.
- Do not load scripts, styles, fonts, icons, or assets from a CDN. Use only the named local npm dependencies and self-hosted Fontsource files, with no commercial or restrictively licensed source.
- Do not output source maps, copy src into dist, exceed a 20 MB dist directory, use absolute asset URLs, or require more than the single npm run build command.
- Do not add client-side routing, bare-directory links, empty href attributes, SEO metadata, Open Graph tags, JSON-LD, sitemap files, or keyword-heavy copy; one index.html, local anchor links, a plain variable-driven title, and an SVG favicon are sufficient.
- Do not generate daily uptime values with Math.random, Date.now, or remote data. Preserve the fixed 90-day series, sample reference range, incident chronology, and consistent component-to-incident status mapping in src/content.ts.
- Do not hard-code Fablegrid-specific copy outside the variable defaults and content file. When variables change, rewrite brand references, service descriptions, component names, support details, and incident narratives coherently.
- Do not rely on green, amber, or red alone to communicate state. Preserve text labels, accessible icons, descriptive chart summaries, visible focus states, labeled controls, keyboard-operable accordions and filters, and reduced-motion behavior.
- Do not allow bar tooltips, navigation, status pills, long email addresses, or incident timestamps to create horizontal overflow or console errors at 1440×900 or 390×844.
